# Reset/save race fix — 30 October 2026

Flutter reset previously ran outside the exclusive save/Sync/restore lock. A payment could be accepted and persisted while the reset HTTP request was in flight, then overwritten by reset's empty queue. A save already queued before reset could also be erased because the pending-work check ran too early.

Reset now reserves a synchronous guard and holds the existing exclusive lock through the server request, replica reload and durable local commit. The pending-work and access checks run after acquiring the lock. Earlier saves make reset stop; new commands during reset fail explicitly in the selected language, so editors retain their input rather than report a successful save. Background Sync waits for reset to finish, and duplicate reset requests are rejected. The guard is released on success or failure. Session/account access is checked again after network awaits before replacing the local workspace.

Settings shows reset progress and disables a second Reset action. Product-retention behavior and server reset rules are unchanged.

Six gated regression tests cover all three asynchronous stages, payment-before-reset ordering and restart persistence, saves after completion/failure, duplicate resets, Sync exclusion and session expiration. Before the fix, five tests failed; after the fix all six pass. The full Flutter suite passes 124 tests and static analysis reports no issues. Evidence: `../releases/flutter-reset-fix-2026-10-30/`.

The fix is included in Flutter 3.0.2 (build 8). Versioned APK/source artifacts and their verification reports are under `releases/`; release build and signing checks are recorded separately in `flutter-v3.0.2-build-evidence/`. The original 3.0.1 APK/source ZIP artifacts remain historical releases without this fix. No live reset, web/Python deployment or business-data change was performed by this task.
